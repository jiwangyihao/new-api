# 以来源快照和移动加权平均维护套餐运营剩余价值

## 背景

ADR 0001 将不限时 Credit 建模为全局唯一的 `credit_balance` 套餐权益：余额套餐本身零价格、不失效、不重置；Basic、Standard、Pro 等计时套餐只在不限时购买时充当有价格和 Credit 数量的充值档位。

生产基线 `f446a1569c2ced54a3fe438b5c4575659a59241d` 的「付费套餐剩余价值」仍沿用旧分析假设：只接受 `SubscriptionPlan.price_amount > 0`，从权益当前关联套餐读取价格，并对所有权益取时间价值与 token 价值的较小值。该假设与 Credit 领域模型冲突。最小复现为：购买 `40 CNY / 1,000 Credit`，消费 200，Credit 权益 `end_time = 0`；活动范围能找到该权益，token 价值是 32 CNY，但最终计入价值和有效付费权益数均为 0。

只取消正价格过滤或给 `end_time = 0` 加特例不能修复来源关联、套餐改价、合并余额、交错消费、退款、欠额和历史数据置信度问题。需要决定价值从哪里来、怎样随 Credit 消费、怎样持久化，以及分析结果能承诺什么。

## 决策

### 1. 指标性质

「运营剩余价值」是在观察时点对尚可交付有价服务的运营估计。它不是会计递延收入、现金负债、可退款金额或订单实收金额。

计价采用履约档位标价：

- Credit 购买使用充值档位的标价快照，不使用促销后或支付渠道实际收款；实际支付继续作为辅助审计信息。
- 兑换使用兑换时充值档位标价。
- 管理员增加 Credit 属于售后授予，必须选择充值档位，并按授予 Credit 占该档位 Credit 的比例估值。
- 计时权益购买、兑换和管理员授予在授予时冻结价格、币种、Credit、期限和规则版本。
- 计时权益转换在确认时先按既有规则计算 `gross_credit = full_31_day_blocks × credit_basis + current_remaining_credit`，再使用源档位权威整数标价与同一个 `credit_basis` 形成未舍入单位价值 `price_amount_micros / credit_basis`，并冻结本次毛 Credit 的价值。该值按规则可确定，置信度为 `exact`，但不表示转换时发生收款。

### 2. Credit 使用物化估值状态

每份 Credit 余额权益维护且仅维护一行 `CreditValuationState`。它与 `UserSubscription.token_limit/token_used` 在同一事务、同一行锁序列中更新，保存：

- 当前可用 Credit；
- 尚未摊销的确值成本微单位；
- 尚未摊销的估值成本微单位；
- 成本基础未知的 Credit；
- 估值币种、规则版本、迁移版本、状态版本和更新时间。

Credit 是合并后的同质余额，不按订单保留 FIFO/LIFO 批次。消费前的单位价值为：

```text
(exact_cost_micros + estimated_cost_micros) / available_credit
```

一次出账按操作前移动加权平均，分别同比例减少确值成本、估值成本和未知 Credit。API 消费、管理员减少、订单退款和拒付都使用同一规则。余额清零或形成结算欠额时，所有微单位舍入余数归零。

入账先抵扣历史结算欠额。只有净新增可用 Credit 及其同比例成本进入估值状态；立即用于偿还欠额的部分代表已经交付的服务，不进入剩余价值。

### 3. 请求退款按请求快照恢复

每次 API 预扣把实际移除的确值成本、估值成本和未知 Credit 份额记录在现有 `SubscriptionPreConsumeRecord`。最终用量减少或请求失败时，按该请求累计扣除快照原样或同比例恢复，而不是按退款时已经变化的池平均值恢复。追加结算按追加发生时的池平均值扣除，并累加到同一请求快照。

结算接口以 `request_id + 目标累计消费量` 对账，重复提交相同目标值是无操作。正向结算合并器可以继续按权益批量开启一个事务，但必须保留请求顺序和 `request_id`，逐请求计算舍入并更新预扣记录；不得只按 `subscription_id` 合并成一个无归属 delta。

高频 API 请求不新增第二份不可变账本。低频购买、兑换、转换、管理员调整、退款和拒付继续写 `CreditBalanceLedger`，并增加结构化估值与汇率快照。

### 4. 计时权益按每次授予冻结估值

同一 `UserSubscription` 会被续期合并，不能只在权益行保存最后一次价格。每次购买、兑换或管理员授予都写一条不可变的计时权益估值授予记录，包含来源幂等键、服务起止、档位标价微单位、币种、Credit、期限/重置规则、置信度和规则版本。

计时权益的时间价值和 token 价值继续取较小值，但计算使用授予时冻结的估值时间线，不再读取套餐当前价格重写历史。来源分组按授予记录聚合；一条合并权益含多个来源时，权益行明确标记为混合来源。

### 5. 金额、舍入和汇率

持久化金额统一使用有符号 64 位整数微单位：`1 currency unit = 1,000,000 micros`。热路径禁止使用浮点数计算成本。所有非负乘除使用无溢出的 `floor(a × b / d)`；部分出账向下取整，最后一笔清空余额时带走全部余数。
套餐标价另持久化为整数微单位，并作为新估值快照的权威来源；现有浮点字段只保留给兼容展示，不进入估值算术。

Credit 使用全局 Credit 余额套餐 `currency` 声明的单一估值币种；尚未转换的计时权益仍按各自授予快照原币种分组：

- Credit 同币种入账按 1:1；
- Credit 的 CNY 与 USD 来源使用入账时 `USDExchangeRate` 的精确十进制有理数快照；
- Credit 的其他新异币种入账拒绝；
- 汇率之后变化不重估存量；
- 历史 Credit 的 CNY/USD 用迁移启动时冻结的汇率，统一标记 `estimated`；无法支持的历史币种记为成本未知；
- 计时权益转换时才换算到 Credit 估值币种，原计时 grant 不做动态 FX 重估。

原订单金额与币种保持不变。

### 6. 置信度和历史迁移

成本基础分为：

- `exact`：前向写入且来源快照、档位、Credit 和汇率完整，或按确定规则冻结的转换；
- `estimated`：历史迁移根据可恢复来源、迁移时汇率和最终余额比例重建；
- `unknown`：缺少可靠价格、Credit 分母、来源关联或支持的汇率。

主「运营剩余价值」可合并确值与估值，但必须同时披露估值金额和未知 Credit；不得把两者都展示为实收或全部精确。

历史迁移不重放请求日志。它汇总可恢复的订单、兑换、转换和管理员来源，然后仅按迁移时最终可用余额比例估算尚未摊销成本。迁移可重跑、版本化且不覆盖前向确值。

### 7. 分析语义

计时权益和 Credit 必须走显式分支：

- 计时权益读取不可变授予估值记录，使用时间/token 双口径。
- Credit 不受余额套餐 `price_amount`、`end_time` 或时间价值公式影响，直接读取物化估值状态。
- Credit 套餐组使用全局余额套餐；由于采用移动加权平均，来源维度只显示「Credit 混合池」，不得伪造某一订单仍剩多少价值。
- `snapshot_at` 继续协调面板的一轮请求，但 Credit 不支持任意历史回放。状态更新时间晚于请求时点时返回 `current_only` 警告和观察到的状态版本；不得把当前值伪装成历史值。

### 8. 深模块与接缝

估值算法集中在 `model/credit_valuation.go` 的深模块中。购买、兑换、转换、管理员调整和请求结算只提供来源事实或目标累计消费量，不自行计算平均值、置信度、欠额比例、FX 或舍入。

模块必须在现有事务接缝内工作：`GrantCreditBalanceTx`、`RecoverCreditBalanceTx`、`AdjustCreditBalance`、`ConfirmTimedSubscriptionConversion`、预扣和请求结算。删除旁路直接修改 Credit `token_limit/token_used` 的能力。
迁移门禁非 ready 时继续旧数量写入并捕获前向来源快照；只有显式迁移 ready 后才强制数量与估值双写。强制双写开放后禁止旧镜像直接回滚；紧急回滚必须先停写并通过维护命令将门禁置为 `suspended`。

## 被否决的方案

### 查询时动态重算

无法区分「先消费后低价充值」与「先低价充值后消费」等具有相同当前余额但不同剩余成本的历史，也无法在不重放高频日志的前提下恢复操作顺序。

### 为每个 API 请求写完整估值事件流

可以任意历史回放，但会为热路径增加永久事件写入和重放复杂度，与 ADR 0001 已选择的「聚合余额 + 低频账本」冲突。

### FIFO 或 LIFO 批次

Credit 在扣费行为上已经完全合并；引入批次消费顺序会制造用户不可见的新业务语义，并使退款、转换和分析来源归属更复杂。

### 按当前平均值退款

预扣与退款之间发生充值时会凭空增减运营价值。请求级扣除快照能在不增加高频账本的情况下精确逆转。

### 使用订单实付或动态汇率

订单实付会让促销和支付渠道差异改变相同服务的运营价值；动态汇率会持续重写历史。两者均不符合指标用途。

## 后果

- 分析读取变为常数级状态读取，热路径多更新同一事务中的一行估值状态和现有预扣记录，但不增加每请求账本。
- 正向 token delta 合并器需要保留请求身份；这是保持舍入和退款可逆性的必要代价。
- 管理员增加 Credit 的接口和 UI 必须新增充值档位选择；旧客户端不提供 `plan_id` 时增加操作会被拒绝，减少操作保持兼容。
- 计时授予增加不可变记录，解决续期合并后价格快照丢失，但历史记录只能估算。
- 新 schema 是附加式的；一旦启用强制双写，回滚到不维护估值状态的旧镜像会造成语义漂移，因此只能在写流量隔离后回滚，正常故障处理必须向前修复。
- 详细字段、迁移门禁、接口兼容和验收见 `docs/superpowers/specs/2026-08-02-credit-operational-remaining-value-spec.md`；实施顺序见对应 plan。
